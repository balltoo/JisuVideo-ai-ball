# 长文短剧生产包方案与分步实施节奏

> 状态：已确认的产品方向。阶段 0 已由 PR #93 完成；本方案后续以“生产包导入最小契约”作为第一个运行时实施任务。
>
> 适用范围：JisuVideo-ai 的「AI 短剧生产工作台」主线。本文不授权平台调用付费模型，也不替代人工对故事、人物和成片的最终判断。

## 1. 一句话定位

平台不再把自己定位成“从任意长篇网文自动去噪和拆分”的工具，而是定位为：

**接收已经可生产的故事材料，统一全剧创作规则，并稳定产出剧本、分镜、提示词、图片和视频的短剧生产工作台。**

长文的去噪、校对、章节整理、初步分集和人工把关，优先在 Work Buddy、CodeBuddy、Codex、Hermes 等外部工具中完成；JisuVideo 负责导入、统筹、生产、复核和追溯。

## 2. 关键决策

### 2.1 长文治理前置到平台外

- 长篇小说、网文、抓取稿不要求在平台内去噪。
- 外部工具先完成去广告、去重复、章节校对、文本修复、初步分集和人工复核。
- 导入平台的长文应当已经是“可作为短剧生产输入”的确认内容。
- 现有原文健康检查和整理能力保留为兼容/辅助能力，不作为长文主流程和产品卖点；不得强制用户在平台内执行。

### 2.2 大纲是项目圣经，不是一段固定提示词

大纲应作为全剧的结构化“项目圣经（Drama Bible）”。它是后续 AI 任务的事实来源之一，但不应被整篇机械拼进每一次模型提示词。

每次任务由系统按需组合“任务上下文包”：

`项目圣经相关片段 + 当前剧集状态 + 关联人物/场景资产 + 当前任务要求`。

例如：生成第 8 集剧本时，取全剧主线、人物当前关系、第 7 集结尾状态、第 8 集目标和第 9 集承接约束，而不是把全书和全部人物资料全部塞入提示词。

### 2.3 人物和场景是全剧资产，不是逐集临时数据

- 人物资产保存固定外观、身份、口吻、动机、关系、秘密、成长线和不可违反项。
- 场景资产保存空间关系、时代、光线、固定道具、视觉设定图和不可改变项。
- 单集只能叠加“本集状态”，例如人物情绪、服装变化、场景时间段；不得悄悄覆盖全剧基准设定。
- 所有角色提示词、场景提示词、分镜提示词与视频提示词均从这些全局资产取得一致性约束。

## 3. 目标输入形态

新建项目时应明确选择内容来源，而不是默认所有内容都进入“平台内去噪”。

1. **短文本创作**：粘贴故事、短文或梗概；保留现有轻量分析与分集路径。
2. **已整理长文**：导入已去噪、校对后的全文；平台只做结构统筹和短剧生产。
3. **已分集内容**：导入逐集正文，跳过平台自动拆分，仅补全大纲和生产资产。
4. **短剧生产包**：一次导入全文、全剧大纲、人物、场景、分集目录与来源说明。

前两种可从全文生成初始大纲和分集建议；后两种以导入结果为主，平台只提示缺失项和不一致项，不擅自重写确认内容。

## 4. 短剧生产包规范（第一版）

第一版优先采用易被人工和外部 AI 工具读取、修改和生成的 Markdown 结构；后续再增加 ZIP/JSON 的一键导入导出。

生产包最小内容：

```text
项目名称、视觉风格、画幅、目标集数
全剧大纲
人物圣经
场景圣经
分集目录
  - 每集目标、冲突、结尾钩子、与上下集关系
  - 每集确认正文（可选；已分集导入时必填）
来源与处理说明
```

建议的文件布局：

```text
drama-package.md                 # 项目元信息与全剧大纲
characters.md                    # 人物圣经
scenes.md                        # 场景圣经
episodes/
  001.md                         # 第 1 集目标、钩子、正文
  002.md
source-manifest.md               # 原始来源、外部处理工具、版本和人工确认说明
```

规则：

- 导入时保留原始文件和导入版本号，不能把外部来源静默覆盖掉。
- 平台应展示解析结果、缺失字段、冲突字段和将要创建/更新的资产，用户确认后才写入项目。
- “已分集正文”优先级高于平台建议分集；平台可以提出重拆建议，但不能自动覆盖。
- 生产包中的“大纲、人物、场景、剧集”分别独立版本化，便于追溯变更来源。

## 5. 项目圣经的数据结构

### 5.1 全剧大纲

- 一句话卖点、题材、受众、情绪基调、画面风格。
- 世界观和现实规则。
- 主线冲突、核心悬念、结局承诺。
- 全剧阶段结构：开局、升级、反转、高潮、收束。
- 时间线、伏笔表、关键道具表、不可提前揭示的信息。
- 每集目标、结尾钩子、上集承接和下集预告。

### 5.2 人物圣经

- 固定身份、年龄、外观、声音/口吻、行为习惯。
- 目标、恐惧、秘密、关系网、成长弧。
- 固定视觉提示词片段、负面约束、设定图和可用参考图。
- 全剧不可变项，以及每集允许变化的状态项。

### 5.3 场景圣经

- 场景名称、时代、地点、空间结构、时间段、光线和氛围。
- 固定布景、关键道具、不可改变的空间关系。
- 场景视觉提示词片段、设定图、可复用参考图。
- 可在单集覆盖的状态项，例如雨夜、停电、凌乱、节日装饰。

## 6. 生产流程调整

```text
外部工具整理长文 / 初步分集
        ↓
导入已整理长文或短剧生产包
        ↓
校验导入内容 → 用户确认项目圣经
        ↓
补齐或复核人物圣经、场景圣经
        ↓
按大纲统筹分集关系与每集状态
        ↓
剧本 → 分镜 → 角色/场景资产 → 提示词 → 图片/视频
        ↓
每一步记录所使用的大纲版本、人物版本、场景版本和剧集版本
```

平台内“原文整理”入口应降级到辅助菜单：用于短文本、小范围检查或旧项目兼容；导入长文/生产包的用户不应被要求先执行该步骤。

## 7. 分步实施节奏

### 阶段 0：方向收口与兼容策略（约 1 天）

- 冻结本文为长文主流程的产品决策。
- 将当前“平台内整理”明确标注为兼容辅助能力。
- 盘点 #74 尚未合入的前端整理向导，调整为不阻塞导入流程的次级入口。
- 产出生产包 Markdown 示例与字段说明，不改动生产数据。

验收：新需求、Issue、PR 描述不再将平台内去噪称为长文必经步骤。

**完成记录（2026-09-07）**：PR #93 已把本方案纳入正式路线。#86–#91 的原文版本与整理向导保留为兼容资产；#75 的运行报告改作兼容链路证据，不能再被引用为长文主流程的验收完成证明。

### 阶段 1：导入已准备内容（约 2–3 天）

- 新建项目增加四种内容来源选择。
- 支持粘贴/上传 Markdown、TXT；已分集内容可直接进入剧集审核区。
- 导入前展示解析预览：标题、风格、画幅、大纲、人物、场景、剧集数量和缺失项。
- 用户确认后再创建项目和资产，不在解析阶段写入正式数据。

验收：一份已整理长文或已分集 Markdown 能不经过平台内去噪，创建可继续生产的项目。

### 阶段 2：项目圣经与大纲板块（约 2–3 天）

- 在项目页新增“大纲与全局设定”板块。
- 支持全文大纲、阶段结构、每集目标/钩子/承接关系、伏笔和禁区的编辑与确认。
- 大纲保存为独立版本；修改后提示会影响哪些未确认剧本、分镜或提示词。
- 分集页显示当前集从大纲继承的目标和上下集关系。

验收：用户能在不读完整原文的情况下，通过大纲理解全剧和任一集的职责。

### 阶段 3：全局人物与场景圣经（约 3–4 天）

- 角色、场景资产增加“全剧基准设定”和“本集状态”两层信息。
- 现有角色/场景设定图与提示词迁移为全局资产可复用，不复制成互相漂移的临时文本。
- 在单集编辑时，仅允许填写状态变化并清晰显示继承来源。

验收：同一人物、场景跨集生成时能够稳定复用基准设定；任何覆盖都有来源和范围。

### 阶段 4：上下文包与生成链路接线（约 3–4 天）

- 为剧本、分镜、角色提示词、场景提示词、H3 视频提示词定义各自所需的上下文包。
- 自动记录每次生成使用的项目圣经、人物、场景、剧集版本号。
- 大纲或全局资产变更后，仅标记受影响的下游内容为“需复核”，不删除已生成成果。

验收：可以解释任意一条提示词“为什么这样写、引用了哪些设定、何时失效”。

### 阶段 5：短剧生产包导入导出（约 2–3 天）

- Markdown 导入稳定后增加 ZIP/JSON 导入导出。
- 外部工具可按同一规范生成生产包，用户在平台内完成预览、映射和确认。
- 提供模板、示例项目和错误定位提示。

验收：外部工具处理的一部代表性长文可重复导入，另一台电脑可复现项目结构。

### 阶段 6：代表样本验收（约 2 天）

- 短文本、已整理长文、已分集生产包各选一个代表样本。
- 验收导入完整性、大纲一致性、跨集人物场景一致性、提示词来源可追溯性和视频生产衔接。
- 真实模型生成涉及费用时，先由用户明确额度；测试结果区分 mock 与真实模型。

验收：形成可复现的代表项目报告，再关闭端到端验收任务。

## 8. 不做什么

- 不在第一阶段重写长文内容或承诺“AI 自动去噪正确”。
- 不把全篇原文、大纲和全部资产无差别塞进每一次提示词。
- 不因修改大纲而直接覆盖已有剧本、分镜、资产或视频。
- 不删除现有原文整理能力和旧项目兼容路径。
- 不在未确认生产包字段含义前，直接进行大规模数据库迁移。

## 9. 建议的 Issue 拆分与负责人节奏

1. **主账号 / Codex**：阶段 0 的方向收口、生产包规范、公共契约和最终审核。
2. **实施线 A**：阶段 1、2，负责导入、项目圣经、大纲和分集关系。
3. **实施线 B**：阶段 3、4，负责全局资产、生成上下文包、失效追踪和生产可靠性。
4. **主账号 / Codex**：阶段 5、6 的集成验收、代表样本、Bugbot 审核和合并裁决。

热点文件（项目页、数据 schema、共享 API 契约、全局生成上下文）必须一次只由一条实施线占用。两个实施线出现依赖时，先由主账号合入最小契约 PR，再分别实现，禁止跨未合入分支依赖。
