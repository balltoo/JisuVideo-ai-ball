## 1. 需求与原始问题

平台已有 9 个 Agent、5 个 Skill、完整的短剧生产流水线骨架，但缺少一份「从零到一、可复现、成本可控」的最小闭环验证记录：没有人从空库开始，用一篇真实题材的原文，把 ①导入原文 → ⑧视频提示词 完整跑一遍并逐环节做数据级验收。

本次以一个具体话题——**「普通上班族如何学习 AI」**——作为素材，目标是：

1. 验证文本链路是否真能端到端跑通（而不是"接口存在"）；
2. 在每个环节做数据库级比对，确认 Agent 的产出符合 Skill 声明的规范；
3. 把暴露的问题整理成可排期的清单，供 owner 决定后续任务优先级。

选择这个话题的原因：职场现实题材天然能提取出多角色/多场景/多道具；有冲突、有反转、有钩子，可拆多集；产出质量一眼可判（是否编造情节、人物是否走样）。

## 2. 本次范围与明确不做的内容

**做了**

- 完整走通 8 个环节：① 导入原文 → ② 项目方案提炼（`project_analyzer`）→ ③ 拆集策划（`episode_planner`）→ ④ 批量建集 → ⑤ 剧本改写（`script_rewriter`）→ ⑥ 资产提取（`extractor`）→ ⑦ 分镜拆解（`storyboard_breaker`）→ ⑧ 视频提示词（`prompt-generator/video-prompt`）
- 其中 ⑤→⑧ 只跑了**第 1 集**（EP02/EP03 未跑）
- 每个环节都做了数据库级验收（字数、条数、绑定关系、规则达标率）
- 唯一的人工干预：补录 1 个被漏提的角色；手工修正剧本 2 处事实错误；手工收敛 1 个场景描述

**明确不做**

- 未执行付费环节：素材图生成 / 分镜图生成 / 视频生成 / 拼接导出
- 未跑 EP02、EP03 的剧本改写及后续环节
- 未修改任何生产代码（本次为纯探针，所有发现均只登记不改动）
- 未清理数据库中的历史测试残留项目（避免误删）

## 3. 关键设计决策与原因

**① 为什么以「视频提示词」为最小闭环终点**
⑨ 之后的生图/生视频/拼接只是把已有提示词喂给媒体厂商，不涉及新的业务逻辑，但要花钱。把终点定在 ⑧，可以用 1 元以内的文本 token 成本覆盖全部 Agent 逻辑与数据链路。

**② 为什么用「真人实拍」风格**
风格预设库里原有 5 条（3D 漫剧 / 日漫 / 吉卜力 / 水彩 / 美漫）**全部是非写实**。而风格库就是 AI 的候选空间——库里没有的东西它永远推荐不出来。为本次题材新增了 `live-action` 风格，这也反证了「风格植入」这个动作的必要性。

**③ 为什么最终按 3 集拆分**
AI 实际推荐 10 集（每集 241–276 字，约 1 分钟），按短剧节奏其实更专业。但每集往后要跑 4 次 Agent，最小案例的目的是**验证链路**而非产出最优化，3 集（12 次调用）足够暴露问题，10 集是 40 次。

**④ 验证方法：以数据库为准，不以 UI 为准**
每个环节都直接查 MySQL 核对，而不是看界面显示的成功提示。这个方法直接挖出了下面第 3、4 项问题。

## 4. 分层问题清单

### 4.1 P0 — 安全

#### P0-1 `GET /api/v1/ai-configs` 明文返回 API Key

- **位置**：`backend/src/routes/aiConfigs.ts:230-237`（路由）+ `:25-31`（`withParsedFields`）
- **现象**：列表接口直接 `success(c, rows.map(withParsedFields))`，而 `withParsedFields` 是 `{ ...toSnakeCase(r), model, temperature }`——把整行字段原样展开，`api_key` 未做任何脱敏。实测调用该接口即可拿到完整密钥明文。
- **影响**：任何能访问该接口的人（浏览器 DevTools、日志粘贴、截图分享、局域网他人）即可获取密钥；密钥通常可直连计费厂商。
- **建议**：
  - 出参统一掩码：保留前 6 位 + `...` + 后 4 位，其余以固定长度占位符替代；
  - `PUT /ai-configs/:id` 接收空 `api_key` 时视为"不修改"，避免前端必须回填明文；
  - 同步检查 `GET /:id`（`:362`）是否存在同样问题。

### 4.2 P1 — 正确性与数据风险

#### P1-1 `script_rewriter` 会改写相对时间，并丢失事实信息

- **位置**：`backend/workspace/skills/script-rewriter/SKILL.md`
- **现象**（EP01 实测，逐句比对原文与剧本）：

  | 类型 | 原文 | 剧本产出 |
  |---|---|---|
  | 事实被改 | 她**上个月**才入职，二十六岁 | 她二十六岁，**去年**才入职 |
  | 信息丢失 | 他在这家公司做了**七年后台运营** | （整句消失） |

- **影响**：这不是笔误，是 LLM 的典型陷阱——改写时模型会把自己"以为的当下"代入，把原文中的相对时间自动换算一遍。本例中"上个月才入职"恰是整段最有力的一刀（入职一个月的新人效率碾压七年的老员工），改成"去年"后反差立刻软掉；而"七年工龄"丢失后，"老员工被优化"的荒诞感也一并削弱。
- **建议**：
  - Skill 增加硬约束：**相对时间表述（上个月/去年/昨天/刚才/下周）一律原样保留，禁止换算或归一化**；
  - 增加：**原文中的年限、工龄、金额、数量等事实性数字必须 100% 保留，不得省略**；
  - 在改写完成后增加一次自动校验：抽取原文中的数字与时间词，与产出比对，缺项时提示人工复核（比如此次 2 处问题靠人工逐句比对才发现）。

#### P1-2 剧本改写面板（Step1）没有保存按钮，保存被隐藏成「下一步」的副作用

- **位置**：`frontend/app/components/EpisodeScriptPanel.vue`（未定义 `save-script` emit）；`frontend/app/views/drama/episode.vue`（`goNextStep()` 约 `2922` 行；`localScript` / `localRaw` 约 `2050` 行）
- **现象**：Step0（原始内容）工具栏有「保存」按钮，Step1（AI 改写）**只有「跳过改写」与「重新改写」，没有保存**。真正的保存逻辑藏在 `goNextStep()` 里：

  ```js
  if (scriptStep === 1 && canGoNext) {
    if (localScript.value.trim()) saveScr()   // 先存剧本
    panel.value = 'production'                // 再跳资产
  }
  ```

  即：**只有点页面底部的「资产」按钮才会保存**。而 `localScript` 是纯内存 `ref`，无落盘、无自动保存，刷新即丢。
- **影响**：本次试跑实际卡在这里——用户改完两处剧本后找不到保存入口，一度以为改动已丢失。此外还导致：无法"改一半先保存、回头再改"；保存反馈只有一闪而过的 toast，无"已保存"状态。
- **建议**：Step1 工具栏补一个显式「保存」按钮复用 `saveScr()`；同时加 debounce 自动保存（约 2 秒）或至少 `beforeunload` 拦截提示。

#### P1-3 `@` 引用解析静默失败：资产图未生成时整张映射表为空

- **位置**：`frontend/app/views/drama/episode.vue` `getShotReferenceIndexMap` / `resolveVideoPromptRefs`（约 `3901-3936`）

  ```js
  const push = (name, url) => { if (!url || seen.has(url) || ordered.length >= 9) return; ... }
  ...
  if (!names.length) return prompt        // 映射表为空 → 整体跳过替换
  return prompt.replace(/@([^\s@]+)/g, (m, raw) => {
    for (const name of names) {           // names 按长度倒序 → 最长匹配优先
      if (raw.startsWith(name)) return `@图片${map[name]}${name}${raw.slice(name.length)}`
    }
    return m })
  ```

- **现象**：`push()` 要求该资产已有图片 URL 才会进入映射表。**一张素材图都没生成时，映射表为空，整个 `@名字` 替换被跳过**，原始文本 `@李建国` 会原样送进视频模型。
- **影响**：这是一处**隐性流程耦合**——"必须先出素材图、再出视频"，否则角色一致性无从保证。但 UI 上没有任何提示，用户只会看到视频里人物脸不一致，难以归因。另外 `ordered.length >= 9` 的 9 张参考图上限也是静默丢弃，无提示。
- **建议**：
  - 资产图缺失时，在分镜/视频面板给出显式警告（如"该分镜引用的角色尚未生成参考图，视频一致性无法保证"）；
  - 提交视频任务前做一次服务端校验；
  - 超过 9 张参考图时明确提示被丢弃的资产名。

  > 附：该替换逻辑本身是正确的——名字按长度倒序 + `startsWith` 匹配，所以 `@李建国穿着洗得发白的蓝灰格子衬衫`（引用＋动作连写，Skill 规定的格式）能被正确切成 `@图片1李建国` + 描述。

### 4.3 P2 — 规则与体验

#### P2-1 默认集数估算公式完全不适用于短剧

- **位置**：`backend/src/services/episode-planning.ts:48-51`

  ```ts
  export function defaultEpisodeCount(contentLength: number) {
    // 初稿按每集约 2500-4500 中文字符估算，限制在 1-30 集。
    return Math.max(1, Math.min(30, Math.round(contentLength / 3500) || 1))
  }
  ```

- **现象**：注释里的"2500–4500 字/集"是**长视频**假设。竖屏短剧单集 1–3 分钟，实际只有 500–1500 字。实测 2635 字原文，此公式给出 **1 集**；而 `episode_planner` AI 实际推荐的 `recommended_count` 是 **10 集**（每集 241–276 字，约 1 分钟）——**兜底值与模型实际行为差了 10 倍以上**。
- **影响**：`recommended_count` 优先，所以只在 AI 返回无效时才用到兜底。但首次使用者若参考界面上这个数字，会严重误判；且兜底值基本是废值。
- **建议**：除数降到 800–1200，或按题材分支；或在兜底触发时明确提示"未能获得 AI 建议集数，请手动指定"。

#### P2-2「调整集数」输入框被 `v-if="episodePlan"` 包着

- **现象**：必须先跑一次「AI 推荐集数」才会渲染出集数输入框，用户无法直接指定集数——**白花一次调用**。
- **建议**：输入框常驻，或提供「指定集数直接拆分」入口。

#### P2-3 `naturalBoundaries` 不识别章节标题，导致切分点与章节边界错位

- **位置**：`backend/src/services/episode-planning.ts:6-12`

  ```ts
  const pattern = /[。！？!?](?:[”’」』])?|\r?\n\s*\r?\n/g
  ```

- **现象**：切点只认句末标点与空行，不认「第X章」。实测三集拆分结果：

  ```
  EP01  第一章 提效风暴 ✓ … 打印机旁，站了很久。
        第二章 三行的答案      ← 标题落在 EP01 的 95% 处
  EP02  他每天学到凌晨一点。    ← 缺了上一句过渡
        …
  EP03  办公室里，苏晚的座位空着。 ← 第二章的末句被带到这
        第三章 下班后的两小时   ← 标题出现在正文之后
  ```

- **影响**：内容一字未丢（已逐字符验证），但观众体验上 EP01 结尾会突然冒出一行"第二章 三行的答案"；EP02 从"他每天学到凌晨一点"冷启动，缺了"为什么突然开始狂学"的前提。
- **建议**：把 `第[一二三四五六七八九十百千]+[章回节]` 设为**最高优先级切点**——章节标题是作者给出的最强语义边界，优先级应高于句号与空行。

#### P2-4 `extractor` 漏提有台词的角色

- **现象**：剧本中明确有外貌描写 + 对白 + 动作的「张姐」，未被提取进 `characters`。而 Skill 的 `role` 字段本就设了「龙套」档，说明平台**预期**提取过场人物。
- **影响**：该角色的分镜无法绑定参考图，生图时会出现"随机脸"。本例影响有限（该角色仅出现 1 场、2 次），但属于规则未被执行。
- **建议**：提示词明确"**凡有台词或近景出场的角色都必须提取**，过场人物 `role=龙套`"。

#### P2-5 `extractor` 的 `appearance` 字数规范无约束力

- **现象**：Skill 要求 `appearance` 写 **300–500 字**，实测 275 / 204 / 194 字，**三个全部不达标**，且越次要的角色越短。
- **影响**：不影响生图可用性，但属"规范与执行脱节"——说明提示词里的量化约束对模型效力很弱。
- **建议**：在 Skill 里加自检步骤（生成后自行数字数，不足则补充细节）；或下调下限并明确"不足必须补足"。

#### P2-6 场景去重规则（地点+时段）会混入「时变元素」

- **位置**：`backend/workspace/skills/extractor/SKILL.md`（去重规则）+ `backend/workspace/skills/prompt-generator/scene-prompt/SKILL.md`
- **现象**：去重按【地点 + 时间段】精确匹配，因此「公司工位·白天」在买课前（桌面应干净）与买课后（贴满课程付款截图）被合并为一个场景，而 prompt 里写死了：

  > 桌面上还散落着**各种课程付款截图与社群二维码**……承载着**一周之内从清爽到混乱的状态变化**

  同一集内有 3 个分镜共用该场景（2 段买课前、1 段买课后），按此基准图生成会让买课前的画面**提前出现付款截图**——既是时间穿越，也是剧透。
- **本次处理**：已手工把该场景 prompt 收敛为**恒定元素**（保温杯 + 卷边全家福 + 常规工位），时变细节保留在分镜级 `image_prompt` 中（该分镜自己的 prompt 已写明"贴满课程付款截图和社群二维码"），信息未丢失。
- **建议**：这是**规则层面的治理项**，不只是个案。建议在 Skill 中明确原则：

  > **场景 = 恒定基准背景**，只描写不随剧情变化的元素（空间结构、固定陈设、光照）；随剧情变化的陈设一律交给分镜级提示词。

  否则每个"同地点跨时段"的题材都会重现同类问题。

#### P2-7 视频提示词产出多余的外层引号

- **位置**：`backend/workspace/skills/prompt-generator/video-prompt/SKILL.md`
- **现象**：3 个分镜出现双层引号——

  ```
  。「王总说：「上个月上面下了指标。……」，只有空调出风口细微的呼呼声在背景里。
  ```

  即模型把整个"X说：「台词」"又用一对「」包了一层。Skill 只要求单层 `角色名说：「台词」`，且**未给正例/反例**。（旁白段落格式反而是对的：`旁白：「内容」`。）
- **影响**：噪点级——不影响画面生成，但会带到 H3 提示词与后续字幕处理。
- **建议**：Skill 的「禁止事项」补充"引号只允许一层，不得用「」包裹整个『角色名说：…』"；并补一组正/反例对照。

#### P2-8 视频提示词时间片分布违规

- **现象**：Skill 规定"按 3 秒为一段，段数 = duration ÷ 3 向上取整"，但实测：

  | 分镜 | duration | 公式期望 | 实际切分 |
  |---|---|---|---|
  | SB03 | 13s | 5 段 | `3+3+3+3+1` —— **末段仅 1 秒** |
  | SB09 | 13s | 5 段 | `3+3+3+4` —— **只有 4 段** |

- **影响**：1 秒的镜头在真实视频里几乎不可用；段数不足会压缩叙事节奏。
- **建议**：Skill 补充余数分配规则，例如"除最后一段外每段 3 秒；余数并入末段，且**末段不得短于 2 秒**"，则 13s 应为 `3+3+3+4`（4 段）或 `3+3+3+2+2`（5 段），并明确二者取哪一个。

#### P2-9 每集标题自带「第N集：」前缀，与前端 `EP 01` 冗余

- **现象**：`episode_planner` 产出的每集标题形如 `第1集：沉默的周一`，而前端卡片左侧已单独渲染 `EP 01`，显示为 `EP 01 · 第1集：沉默的周一`。
- **建议**：在 `normalizeEpisodePlan` 或提示词中剥掉前缀。

#### P2-10 `extractor` 道具规则与「生活流」题材存在结构性冲突

- **现象**：道具判定三问（①删掉它剧情还成立吗 ②是否只是随手使用的日常物品 ③是否属于场景陈设）会把保温杯、卷边全家福这类**生活质感元素全部过滤**。而"贴近真实生活"的观感恰恰来自这些细节。
- **说明**：这不是 bug，是取向问题——`extractor` 是纯剧情驱动，而道具图是**白底单品图**、生成成本高，只有"引发剧情转折 + 后续要给特写"的东西才值得单独建资产。这个权衡本身是合理的。
- **观察**：实测 `extractor` **已自发**把这些元素降级写进了场景 prompt（"隔板上贴着女儿画的全家福（边角已卷起）""桌面摆着保温杯"），说明提示词里已有类似倾向。
- **建议**：把这条隐含做法**显式写进 Skill**（"质感类小物件不建独立道具，写进场景 prompt"），避免因题材不同而漂移；或为写实题材提供分支规则。

#### P2-11 参考图 9 张硬上限静默丢弃

- **位置**：`getShotReferenceIndexMap`（`frontend/app/views/drama/episode.vue`）`ordered.length >= 9`
- **现象**：顺序为 场景图 → 角色图 → 道具图，第 9 张之后静默丢弃，无任何提示。本次单段最多绑 3 个资产，未触及；但角色多的项目会踩到。
- **建议**：超限时在 UI 上明示被丢弃的资产。

#### P2-12 资产配置带内存缓存，改完可能不生效

- **位置**：`backend/src/services/ai.ts` `getActiveConfigWithId`
- **现象**：配置读取有内存缓存，在设置页改完配置后，后端可能仍使用旧值，表现为"明明改了却报错"。
- **建议**：配置写操作后主动失效缓存；或至少在文档中注明需重启后端。

### 4.4 P3 — 文档与低风险

#### P3-1 README 功能宣称超出实际实现（字幕 / 配音 / 音轨）

- **位置**：`README.md:61` —— `- ✅ FFmpeg 单镜头合成与字幕处理`
- **核查结果**：

  | 能力 | 实际实现 |
  |---|---|
  | FFmpeg 拼接 | ✅ `backend/src/services/ffmpeg-merge.ts`（含音轨一致性判断与 `-c copy` 回退） |
  | 字幕处理 | ❌ `subtitle_url` 仅在 `db/schema.ts:194` 声明、`utils/cleanup.ts:82` 引用，**无任何写入实现** |
  | 配音 / 音轨合成 | ❌ 无实现；音频仅透传各镜头视频自带音轨 |

- **建议**：README 改为"FFmpeg 整集拼接（音频透传）"，把字幕与配音标注为规划中能力。
- **说明**：本次试跑未进入拼接环节，结论来自代码核查，非运行时验证。

#### P3-2 `source_versions` 懒生成机制缺文档说明，易被误判为 bug

- **现象**：新建项目后 `dramas.current_source_version_id` 为 `NULL`、`source_versions` 无记录。实测该状态**完全正常**——首版快照在**拆集策划**时才生成（`routes/dramas.ts` 约 `622` 行 `ensureSourceVersion`），生成后指针正确回填（本次得到 `source_versions.id=85`，2635 字）。
- **说明**：源码注释已写明（"旧项目零回填 / `POST /dramas` 行为不变：本模块不参与创建链路"），但**用户文档缺失**。
- **建议**：在流程文档中补一句说明，避免使用者对着 `NULL` 排查。

#### P3-3 Markdown 感知缺失：从渲染视图复制会静默丢失标题标记

- **现象**：实测原文 2647 字经"复制粘贴"后入库为 2635 字，差 12 字符，经逐字符 diff 定位为 6 处删除（3 个 `## ` 前缀 + 3 个标题后空行）——**正文一字未少**。
- **根因**：`importLocalSourceFile`（文件导入）只做 UTF-8 解码 + 去 BOM + trim，本身没问题；用户是从**渲染后的页面**复制，Markdown 标题被渲染成样式，`## ` 自然不在了。
- **建议**：导入区加提示"建议直接上传 .txt/.md 文件，避免复制丢失格式"；或在字数与预期不符时给出提示。

#### P3-4 分镜未绑定在场的角色（低风险）

- **现象**：两个广角镜头的场景描述里有"会议室里坐着二十来号人"，主角应在其中但未绑定参考图。生图时他会以"随机脸"出现在背景。
- **建议**：风险低（背景人群），可暂不处理；若做一致性收紧，可在 `storyboard_breaker` 提示词中要求"角色在场即绑定，无论是否为主体"。
